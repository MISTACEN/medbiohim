# MEDBIOHIM — режимы работы команды агентов

## Принцип

Команда масштабируется под задачу. Не нужно запускать всех специализированных агентов и субагентов каждый раз. Субагент — инструмент декомпозиции, а не обязательная ступень. Лишний субагент увеличивает накладные расходы, риск конфликтов и время интеграции.

Термины:
- **Координатор** — верхнеуровневый архитектор; распределяет работу между ведущими, согласует контракты и интегрирует результат в `main`.
- **Ведущий агент / полноценный агент** — владелец отдельного workstream (например, Frontend или Backend). Сам может выполнить работу или делегировать части.
- **Субагент** — исполнитель узкой подзадачи, подчиняется одному ведущему и сдаёт ему patch/отчёт.
- **QA/Security** — независимая проверка. Это роль контроля, не обязательно постоянный участник каждой маленькой задачи.

Координатор не считается одним из ведущих исполнителей. Если пользователь говорит «два полноценных агента», это два workstream owner под координатором.

## Режимы

### S0 — один агент, без субагентов

**Состав:** координатор/ведущий-исполнитель или один назначенный агент; 0 субагентов.

**Использовать, когда:**
- задача затрагивает один файл или один небольшой модуль;
- задача последовательная или исследовательская;
- разделение потребует больше синхронизации, чем даст выигрыша;
- есть один общий/конфликтный файл.

**Порядок:**
1. Изучить задачу, актуальный `main`, инструкции и тесты.
2. Выполнить исследование и изменения в одном изолированном workspace.
3. Проверить diff и тесты.
4. Передать результат на независимый QA-проход (или провести read-only review отдельным исполнителем, если доступен).
5. Координатор интегрирует и отчитывается.

**Пример:** исправить один API endpoint вместе с его тестом, если они принадлежат одному модулю.

### S1 — один ведущий + два субагента

**Состав:** один ведущий агент и до двух субагентов. Субагентов может быть 0, 1 или 2.

**Использовать, когда:** есть одна основная область ответственности, которую можно разделить на независимые части.

**Пример для Backend:**
- Backend Lead: фиксирует контракт endpoint, владеет route integration.
- Subagent A: исследует auth/validation и готовит patch только в отдельном middleware/helper.
- Subagent B: готовит тест-кейсы/тесты в выделенных test files.
- Backend Lead: проверяет оба результата, интегрирует их в свой workspace и возвращает единый patch координатору.

**Ограничение:** если route и тесты используют общий файл, назначить одного владельца; субагент может только дать рекомендации.

### M1 — два ведущих агента, без субагентов

**Состав:** координатор + два ведущих агента; субагентов нет.

**Использовать, когда:** задача пересекает два слоя, но внутри каждого слоя работа достаточно связная.

**Пример:**
- Frontend Lead: UI, состояния загрузки/ошибок и вызов согласованного API.
- Backend Lead: Worker endpoint, validation, auth и server tests.
- Координатор: до начала фиксирует URL, method, request/response schema и auth contract; затем собирает два patch независимо.

**Порядок:**
1. Координатор фиксирует общий API/DB контракт и acceptance criteria.
2. Frontend и Backend работают параллельно в разных workspace и по своим файлам.
3. Каждый ведущий запускает свои проверки и сдаёт patch.
4. QA проверяет сквозной сценарий и совместимость.
5. Координатор интегрирует patches по очереди, затем запускает общие проверки.

**Не использовать:** если оба агента должны одновременно менять один общий type, route registry, package manifest или миграцию. Сначала выделить одного владельца общего файла.

### M2 — два ведущих агента, у каждого по два субагента

**Состав:** координатор + два ведущих агента + до четырёх субагентов (по два на ведущего). Каждый ведущий вправе запустить только одного субагента или не запускать ни одного.

**Использовать, когда одновременно выполняются условия:**
- есть два больших и самостоятельных workstream;
- каждый workstream можно разделить ещё на две независимые подзадачи;
- границы файлов и интерфейсов понятны заранее;
- объём оправдывает дополнительные handoff/review.

**Пример для крупного учебного функционала:**
- **Lead A — Frontend**
  - Subagent A1: отдельные UI-компоненты/страница по согласованному контракту.
  - Subagent A2: доступность, адаптивность и frontend tests в выделенных файлах.
- **Lead B — Backend**
  - Subagent B1: отдельный service/helper или исследование auth/validation.
  - Subagent B2: независимые Worker tests / contract tests.
- **Coordinator:** утверждает API контракт и ownership до старта, принимает единый patch от каждого ведущего, интегрирует их последовательно.
- **QA/Security:** проверяет общий пользовательский сценарий, auth/RLS и регрессии независимо от авторов.

**Правило:** субагенты A не подчиняются Lead B и наоборот. Они не передают patches друг другу напрямую для интеграции; межпоточные вопросы идут через координатора или согласованный контракт.

### H — гибридная команда

**Состав:** 1–3 ведущих агента, у каждого 0–2 субагента.

**Использовать, когда** направления разного размера. Например, Frontend может работать самостоятельно, Backend взять одного субагента для тестов, а Education — двух предметных субагентов для параллельной подготовки разных материалов.

Не нужно искусственно выравнивать число субагентов у ведущих.

## Как решить, нужен ли субагент

Ведущий запускает субагента только если:
1. Подзадачу можно описать отдельным deliverable и acceptance criteria.
2. Можно выделить непересекающиеся writable files или read-only исследовательскую задачу.
3. Есть реальная выгода от параллельного исполнения после учёта передачи контекста и review.

Если нет — ведущий делает работу сам. Исследовательский субагент может не иметь права записи вообще.

## Распределение ответственности

| Уровень | Отвечает за | Не имеет права |
|---|---|---|
| Координатор | Общая декомпозиция, контракты между workstream, ownership, интеграция в main, итог | Одновременно писать в workspace исполнителей или пропускать QA gate |
| Ведущий | План своего workstream, выдача узких задач субагентам, проверка их patches, сборка собственного patch | Менять чужой workstream или напрямую интегрировать в общий main |
| Субагент | Только назначенный deliverable и разрешённые файлы; отчёт и patch своему ведущему | Самостоятельно менять scope, писать в незарезервированные файлы, коммитить в main |
| QA/Security | Независимая проверка и блокировка при критических проблемах | Считать непроверенное утверждение доказательством |

## Очередность при общих файлах

Если несколько workstream требуют один и тот же файл:
1. Координатор назначает единственного временного owner.
2. Owner готовит изменение общего файла/контракта первым.
3. Остальные агенты используют его как read-only dependency.
4. После интеграции общего элемента координатор выдаёт обновлённый base SHA и разрешает продолжить.
5. Никаких параллельных правок одного файла даже если агенты работают в разных ветках/worktree.

## Контрольная таблица перед запуском

| Вопрос | Если «да» | Если «нет» |
|---|---|---|
| Есть 2 независимых workstream? | Можно назначить 2 ведущих | Один ведущий |
| Внутри workstream есть независимые подпакеты? | Можно дать субагента | Ведущий делает сам |
| Файлы подпакетов не пересекаются? | Допускается параллельная запись | Один owner или последовательная работа |
| Контракты между слоями определены? | Можно запускать параллельно | Сначала contract/design phase |
| Есть независимая проверка? | QA gate обязателен перед интеграцией | Назначить reviewer; автор не утверждает собственную работу |

## Ограничения MEDBIOHIM

- Все исполнители работают в отдельных worktree/container/patch workspace; общий checkout один за раз использует только координатор при интеграции.
- Основная линия — `main`; постоянные ветки и PR не создаются по умолчанию.
- Субагенты сдают patch ведущему; ведущие сдают итоговые patches координатору.
- Координатор интегрирует patches последовательно, проверяя актуальный HEAD после каждого шага.
- Изменение Supabase schema/RLS, production secrets, Cloudflare bindings, DNS, storage deletion и deploy требует отдельного разрешения пользователя.
- QA/Security — отдельный gate; для маленьких задач проверка может быть компактной, но не должна исчезать.
- Если агентный runtime не поддерживает worktree/sandbox isolation, не имитировать параллельную запись: переключиться на последовательные patches.

## Шаблон назначения команды

```text
Task:
Base main SHA:
Mode: S0 | S1 | M1 | M2 | H

Coordinator:
Workstream A lead:
  Subagents: 0 / 1 / 2
  Writable files:
  Read-only dependencies:
  Deliverable:
  Checks:

Workstream B lead (if needed):
  Subagents: 0 / 1 / 2
  Writable files:
  Read-only dependencies:
  Deliverable:
  Checks:

Shared contracts:
QA/Security reviewer:
Integration order:
Production actions allowed: none unless explicitly approved
```
