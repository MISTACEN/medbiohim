# MEDBIOHIM → PdfMentor: план миграции документного контура

**Дата:** 2026-11-20, сверено с кодом 2026-11-21. **Основание:** [целевая архитектура](MEDBIOHIM_PDFMENTOR_TARGET_ARCHITECTURE.md).
Текущее состояние рабочей копии, порядок деплоя и этапы — в
[handoff](../HANDOFF-MEDBIOHIM-PDFMENTOR-2026-11-21.md).

Правило миграции: **ничего не удаляем до parity**. Старый просмотрщик, поиск и
аннотации MEDBIOHIM остаются рабочими, пока PdfMentor не закрывает тот же
сценарий (и это проверено на двух учётках).

---

## 1. Что переходит, а что остаётся

| Функция | Итог |
|---|---|
| Просмотр PDF, лекций, методичек | PdfMentor |
| Поиск по содержимому документов | PdfMentor |
| Выделения, закладки, заметки к документам | PdfMentor |
| OCR сканов и фото страниц | PdfMentor |
| Разметка BASE / MAIN / ADVANCED, маршрут | PdfMentor |
| ИИ-объяснения по документу | PdfMentor |
| Загрузка, владение оригиналом, версии | MEDBIOHIM |
| Связь документа с предметом, темой, группой | MEDBIOHIM |
| Права доступа, публикации, отзыв | MEDBIOHIM |
| Тесты, билеты, проверка схем, оценки | MEDBIOHIM |
| Прогресс, слабые темы, рекомендации | MEDBIOHIM |
| Атлас препаратов и диагностикум | MEDBIOHIM |
| Office-форматы (DOCX/XLSX/PPTX/CSV) | MEDBIOHIM (File Engine остаётся) |

## 2. Пакеты работ

### P0-A. Укрепление Bridge — выполнено

- одноразовые коды в Upstash Redis (`mentor:sso:*`, TTL 60 с, `getdel`);
- `POST /sso/exchange` только с HMAC (`x-bridge-signature`), rate-limit, аудит
  в структурный лог без кода;
- адрес PdfMentor только из `PDFMENTOR_URL` (https или loopback);
- фронтенд отправляет код POST-формой, `localhost` больше не захардкожен;
- модуль разнесён: `routes/mentor.ts` (оболочка) + `routes/mentor/{model,store,index}.ts`;
- тесты: `workers/api/test/mentor-bridge.test.js`.

### P0-B. SSO в PdfMentor — выполнено

- `users.password_hash` стал nullable: аккаунт из MEDBIOHIM входит без пароля;
- `external_identities(provider, subject, user_id, email, email_verified)` +
  уникальный индекс `(provider, subject)` + RLS-политика;
- миграция `0004_wise_preak.sql`;
- резолвер: identity → подтверждённый email → новый аккаунт; неподтверждённый
  email при занятом адресе — отказ (`email_taken`);
- `POST /login/sso` (form_post), `intent=link` требует сессию PdfMentor;
- `/settings/connections`: список связей и отвязка; последний способ входа не
  отвязывается;
- тесты: `packages/db/src/identity.test.ts` (PGlite + настоящие миграции).

### P0-C. Document Bridge — MEDBIOHIM-половина готова

Сделано (в этом репозитории):

- `POST /api/v1/mentor/documents/access` — проверка прав: файл активен, группа
  специальности пользователя активна, файл на подключённом хранилище; ответ
  `200 { allowed: false }` вместо раскрытия причины через HTTP-код;
- `GET /api/v1/mentor/documents/:id/content?user_id=…` — поток байтов, права
  проверяются на **каждом** чтении, `Cache-Control: private, no-store`, без
  редиректа на подписанный URL (иначе выданная ссылка жила бы после отзыва);
- подпись сервер-сервер: `HMAC(BRIDGE_SECRET, "<ts>.document:<file_id>:<user_id>")`,
  плюс `±120 с` и rate-limit 120/мин на пользователя; `MENTOR_ENABLED=0` — 503;
- аудит каждого чтения и отказа — `bridge_document_reads` (RLS без политик,
  пишет только service-role);
- DoD в части MEDBIOHIM: две учётки не видят чужие файлы (права по группам и
  владельцу ключа); отзыв группы действует со следующего запроса.

Осталось на стороне PdfMentor: `external_sources` (`provider`,
`external_file_id`, `version`, `checksum`, `access_mode`), конвертация форматов
и кэш страниц. Без этого PdfMentor не умеет вызвать бридж.

Важно: включение бриджа в production — отдельное решение владельца (152-ФЗ);
по умолчанию режим выключается `MENTOR_ENABLED=0`.

### P0-D. Встроенный режим — страница материала готова

Сделано:

- `/mentor/lecture/[materialId]` — карточка материала (предмет → модуль → тема),
  вход в PdfMentor по SSO и открытие документа в **существующей** читалке
  `/reader?material=…`; второй просмотрщик не заводился;
- SSO вынесен в `src/lib/mentor-sso.ts` (form_post, адрес только из env) —
  страница `/mentor` и страница материала используют один код, дубля нет;
- `getMaterial(id)` и путь `endpoints.content.material` — чтение одного материала
  с источником;
- честное состояние: пока PdfMentor не умеет открывать внешние документы, блок
  PdfMentor — только вход в среду с пояснением, где читать документ сейчас.

Parity-чеклист замены старого просмотрщика (статус на сегодня):

| Шаг | Статус |
|---|---|
| открыть материал | готово (читалка MEDBIOHIM) |
| найти по тексту | готово (читалка) |
| выделить и заметка | только в PdfMentor, в MEDBIOHIM нет |
| скачать | готово (`/files/:id/download`) |
| доступ по группе | готово (RLS + бридж) |
| отзыв доступа | готово (проверка на каждом чтении) |
| открыть документ внутри PdfMentor | заблокировано стороной PdfMentor |

Старый просмотрщик остаётся включённым до закрытия parity; отдельного флага для него
не заводилось — режим PdfMentor управляется `MENTOR_ENABLED`, а читалка MEDBIOHIM
работает всегда.

### P1-E. Методические карточки препаратов — данные, API и сортировка готовы

Сделано:

- миграция `database/migrations/20261120_preparation_guides.sql`: таблицы
  `preparation_guides` и `preparation_structures`, RLS на чтение для
  авторизованных, идемпотентные `upsert`-ы;
- сид на 18 препаратов из `src/data/histology-preparations.json` (теперь с
  `steps`, `structures`, `system`), SQL собирается скриптом
  `scripts/preparation-guides-sql.mjs` — контент правится в JSON, не в SQL;
- API `/preparations/guides`, `/preparations/guides/:key`,
  `/preparations/structures`; до применения миграции отдаётся пустой список с
  `migrated: false`, атлас не падает;
- атлас: фильтры «структура → орган → ткань → сложность» (совместимы с
  поиском и темами), панель «Методика поиска» в просмотрщике, подписи
  сложности; старые deep-links не менялись;
- тесты: `workers/api/test/preparations-guides.test.js` (контракт API,
  идемпотентность миграции, покрытие 18 препаратов, словарь структур) и
  блок «методические карточки» в `src/lib/__tests__/histologyAtlas.test.ts`.

Админ-редактор готов: `/admin/preparation-guides` +
`PUT /api/v1/admin/preparation-guides/:key` (валидация, upsert по `key`, запись
только `admin` через service-role).

Осталось: заполнение `sources` (колонка в схеме есть, редактор её пока не
показывает — привязка к страницам методички появится вместе с Document Bridge),
сопоставление гидов с реальными `trainer_feed_cards.id` там, где названия
расходятся (сейчас работает нормализация + вхождение названия).

### P1-F. Диагностикум — готов (5 режимов, подсказки, статистика, повторение ошибок)

Старый каркас на 6 захардкоженных разделах и `GET /random` заменён модулем
`workers/api/src/routes/diagnosticum/`:

- `model.ts` — чистые правила: сборка задания (`identify` / `structures` /
  `differential` / `complex` / `schema`), подбор карточки с изображением по названию,
  проверка набора ответов (`missing` / `extra`), 4 уровня подсказок;
- `shared.ts` — загрузка гидов, изображений и словаря структур, чтение попытки;
- `index.ts` — обзор разделов и `POST /start`; `session.ts` — `/hint`, `/answer`,
  `/stats`, `/mistakes` (уникальные `card_id` неверных попыток для повторения);
- ключ ответа хранится в строке попытки (`diagnosticum_attempts.answers`) и не
  входит в колоночные гранты, поэтому до ответа его нет в браузере;
- подсказки открываются только по порядку, каждая −10 баллов; часть задания
  засчитывается лишь при точном наборе;
- статистика: точность, средний балл, разбивка по режимам и разделам,
  `weak_sections` для следующей тренировки;
- UI: `/trainers/diagnosticum` (карточка в списке тренажёров), изображение,
  выбор вариантов, подсказки, разбор и панель методички после ответа.

Осталось: вопросы по `trainer_atlas_cards.annotations` (точечные подписи) —
сейчас структуры берутся из гида; свободный текстовый ответ не оценивается
автоматически и не запрашивается.

Тесты: `workers/api/test/diagnosticum.test.js` (контракт, RLS, отсутствие ключа
в ответе старта) и `src/lib/__tests__/diagnosticum-model.test.ts` (13 проверок
сборки, оценки и подсказок, включая режим `schema`).

### P1-G. Проверка схем — готово (пятый режим диагностикума)

Сделано как «единый режим с двумя осями», без второго движка заданий:
диагностикум получил режим `schema` — «Схема препарата».

- Ось 1 «соответствие источникам»: в задании перемешаны признаки препарата из
  гида и признаки чужих препаратов; студент отмечает только свои.
- Ось 2 «понимание»: по отобранным признакам нужно выбрать сам препарат из
  вариантов — проверяется вывод, а не узнавание названия.
- Балл — среднее по двум частям (часть засчитывается только при точном наборе),
  подсказки и штрафы общие с остальными режимами.
- «Правки возвращаются на рисунок»: после ответа на карточке препарата
  показывается разбор — пропущенные и лишние утверждения, правильный вывод и
  ссылка на методичку; отдельный слой пометок поверх изображения не заводился.

Ограничение: режим работает от `guide.features` (нужно ≥2 признака), поэтому
для гидов без признаков задание честно не строится, а `start` сообщает, что
не хватает данных.

Тесты: `src/lib/__tests__/diagnosticum-model.test.ts` (две оси, отсутствие
ключи ответа в вопросе, пустые признаки), `workers/api/test/diagnosticum.test.js`
(режим в БД и в модели).

### P2-I. Offline-first — очередь ответов готова

Сделано:

- `src/lib/offline/` — IndexedDB-очередь (`outbox`) с правилами: отправка по
  порядку, остановка на сетевой ошибке, снятие окончательного 4xx, лимит 200
  записей; каждая запись помечается `origin: "user"` и получает `client_id`;
- `answerTrainerCard` пытается отправить сразу, при `NETWORK`/`TIMEOUT` кладёт
  ответ в очередь, а UI показывает «сохранён на устройстве» и идёт дальше;
- идемпотентность на сервере: `POST /trainers/feed/answer` помнит результат по
  `client_id` (Redis, TTL 7 дней) и возвращает его с `replayed: true` вместо
  второго ответа; `origin` принимается только `"user"` (иначе 422);
- `OfflineIndicator` в layout: «ждут сети: N», автоотправка при `online` и ручная
  кнопка «Отправить»;
- service worker не изменился в части данных: `/api/` и `/auth/` не кэшируются,
  офлайн остаются только оболочка и `/offline.html` — персональные данные в
  Cache Storage не попадают.

Ограничение: офлайн нельзя проверить правильность ответа — ключ считает сервер,
поэтому ответ уходит в очередь без оценки. Кэш чтения (атлас/гиды офлайн) не
заводился: это отдельное решение по приватности общего браузерного кэша.

Тесты: `src/lib/__tests__/offline-queue.test.ts`,
`workers/api/test/offline-answers.test.js`.

### P2-H — после Document Bridge

Связка с тестами (ошибка → `/mentor/focus`) — на этап после Document Bridge.

Локальная половина P2-H уже работает без PdfMentor: ошибка диагностикума — это
конкретная карточка, поэтому `GET /diagnosticum/mistakes` отдаёт уникальные
`card_id` неверных попыток, а страница диагностикума ведёт по deep-link
`/trainers/feed/histology?cards=…` в существующий тренажёр. Отправка ошибки в
`/mentor/focus` ждёт Document Bridge и решения по 152-ФЗ.

## 3. Parity-критерий замены

Старый контур выводится только когда одновременно:

1. студент открывает все ранее доступные материалы из MEDBIOHIM без повторного входа;
2. преподаватель управляет публикациями и доступом;
3. заметки и выделения не потеряны;
4. отзыв доступа закрывает документ немедленно;
5. две учётки не видят чужие документы (проверено вручную и тестом).

## 4. Проверки

MEDBIOHIM: `npx tsc --noEmit`, `npm test`, `cd workers/api && npm run check`,
`npm run lint`, `npm run build`, `node scripts/predeploy-audit.mjs`.
PdfMentor: `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm infra:dev`.
E2E SSO: вход → обмен → сессия → выход; повтор кода → 401; чужая подпись → 401;
привязка/отвязка без потери аккаунта.
