## 1. Продукт и границы проекта

MEDBIOHIM — самостоятельная образовательная платформа для самоподготовки студентов к экзаменам, тестам, зачётам и занятиям. Это **не официальный сайт вуза и не замена официальному порталу**. Основной ориентир — практическая польза студенту и учебной группе, без коммерческой модели в текущем замысле.

Обязательные продуктовые принципы:
- Сохранять одобренную структуру сайта, навигацию и удачные элементы дизайна; улучшать существующие экраны, а не создавать параллельный интерфейс или делать глобальный редизайн без просьбы.
- Студент сам управляет своей подготовкой. Общие учебные сведения могут вноситься участниками своей группы, а персональное выполнение/сдача задания учитывается отдельно.
- Любая точка добавления домашнего задания (сайт, Telegram, в будущем расширение) должна приходить к одной канонической модели, с проверкой группы и учебного контекста на сервере.
- Реальные импортированные вопросы сохраняют источник и происхождение. Ответы ИИ/непроверенные данные не выдаются за официальный ключ.
- Не хранить пароли от стороннего EIOS в расширении, не обходить CAPTCHA/2FA и не импортировать данные без явного действия/предпросмотра пользователя.
- Платная модель ИИ не должна быть обязательной для базовой полезности. Любая интеграция должна иметь ручной или не-ИИ fallback.

## 2. Архитектура и окружения

- Frontend: Next.js в корне репозитория; Vercel связан с GitHub и обычно разворачивает изменения из репозитория автоматически. Автодеплой не равен подтверждённой работоспособности.
- Backend: PHP API в `backend/`, предназначенный в том числе для размещения на SpaceWeb. Для продакшена нужно отдельно подтвердить PHP-версию/путь/конфигурацию.
- Данные и авторизация: Supabase/PostgreSQL, миграции в `database/migrations/` и backend migrations. Миграции в репозитории не означают, что они применены к production.
- Медиа: существующий атлас использует папку `content`; отдельные изображения/архивы размещались на SpaceWeb; Backblaze B2 — приватное хранилище с настроенным бакетом `medbiohim-files` (EU endpoint, сведения из предыдущей настройки проекта). Не переносить весь архив в ограниченную бесплатную базу Supabase.
- Telegram: отдельное приложение Node/Vercel в `integrations/telegram-bot/` плюс PHP ingestion service и маршрут в backend.
- GitHub Actions — основной задуманный путь автоматических проверок и упаковки, но в последней серии он блокируется до выполнения шагов.
- Секреты, токены, приватные ключи и production-конфигурация не должны коммититься в репозиторий.

- В README зафиксировано, что **у Telegram-бота должен быть один зарегистрированный webhook**: Telegram → Node/Vercel → (опционально) PHP. Нельзя назначать один bot token одновременно на два независимых webhook.
- Relay — только транспорт. Он не доказывает, что PHP корректно распознаёт сообщение как ДЗ, что Telegram-чат привязан к правильной группе или что запись появилась в БД.

Наблюдение по предыдущим завершившимся запускам: они падали примерно через 2–3 секунды, `runner_id=0`, `runner_name=""`, `steps=[]`; журналы заданий не удаётся получить. Часть новых запусков на момент первого чтения ещё выполнялась, но следующая выборка показала failure до шагов. Это свидетельствует о проблеме до выполнения команд, но доступные данные не раскрывают точную причину. Не утверждать без проверки, что причина точно в YAML, коде или конкретной настройке GitHub.

Порядок восстановления:
1. Открыть Actions в репозитории и проверить доступность/разрешения GitHub Actions, лимиты, отключённые workflow, политику организации/аккаунта и hosted runner provisioning.
2. Добиться, чтобы хотя бы один job реально получил runner и показывал шаги.
3. Запустить workflow заново на последнем `main`.
4. Проверить Node `npm test`, PHP синтаксис и regression tests, frontend build, smoke tests, архив backend.
5. Зафиксировать фактический результат и логи. Не маскировать проблему пропуском workflow и не объявлять зелёный статус по наличию файлов тестов.

## 6. Бесплатность и лимиты

- Telegram Bot API сам по себе бесплатен.
- GitHub Free, Vercel Hobby и Supabase Free могут покрыть небольшой учебный проект, но имеют лимиты/условия, которые могут изменяться. Это не обещание абсолютной бесплатности, безлимитности или гарантированного uptime.
- Существующий PHP-хостинг SpaceWeb учитывается как уже имеющаяся инфраструктура; его фактический тариф и лимиты отдельно не перепроверялись в этом проходе.
- ИИ-интеграция необязательна и потенциально платная. Не включать платный API как обязательную зависимость Telegram или домашних заданий.
- Не добавлять Supabase service-role key во frontend/Vercel ради простоты. Использовать узкий серверный маршрут и RLS/проверки доступа.

## 7. Общий реестр проекта: основные направления и известные риски

Это сводка накопленных требований и исторически найденных проблем, а не утверждение, что каждая из них повторно воспроизведена в этом проходе. Перед закрытием любого пункта требуется повторный аудит текущего кода и целевой среды.

### Auth, роли и доступ
- В проекте исторически присутствовали роли student/teacher/moderator/admin, хотя продуктовый сценарий не должен строиться вокруг роли преподавателя как обязательного участника.
- Проверить самоназначение ролей, серверную проверку группы, регистрацию и получение профиля/ролей/групп/курса/семестра.
- Исторические ошибки: отсутствующие/неполные `/auth/register`, `/auth/me`; bearer/dashboard `UNAUTHORIZED`; auth/schedule 401; отсутствие или некорректное получение настроек аккаунта (`AccountSettingsService::getPreferences()` — ранее отмечался fatal, позже сообщалось о добавленном методе и тесте; подтвердить текущую реализацию).
- Проверить RLS всех пользовательских таблиц, в том числе домашних заданий/сдач, ролей, файлов и контента. Не считать наличие SQL migration доказательством применения миграции.

### Домашние задания, расписание, посещаемость
- Общее ДЗ создаётся участником своей группы; права на редактирование/удаление отдельно ограничены.
- Индивидуальное выполнение/сдача не должно смешиваться с общей записью задания.
- Проверить связь ДЗ с днём, предметом и парой; прикрепление фото; отображение в расписании; отметки выполнения.
- Исторические риски: рассогласование UI/API по разрешениям, проверка статуса `cancelled`, привязка предмета/группы/расписания, вложения и fallback paths.
- Расписание должно поддерживать неделю/месяц/семестр, пересечения пар, предметные цвета, добавление занятий, посещаемость (уважительная/болезнь/неуважительная) и пробелы знаний.

### Тесты, билеты, вопросы и проверка ответа
- Все пользователи должны иметь доступ к просмотру банка вопросов и корректных ответов в учебном режиме без запуска экзаменационного теста, с учётом прав публикации.
- Поддержать single/multiple choice, свободный ответ, несколько правильных ответов, последовательное прохождение, нумерацию, редактирование администратором и жалобу на вопрос.
- Проверка свободного ответа должна учитывать смысл, а не орфографию; вызов ИИ опционален, точное совпадение можно обработать локально.
- Источник, правильность, статус проверки и версия вопроса должны быть различимы. Не заменять старый банк новыми данными без согласования.
- Проверить сохранение попыток, snapshots ответов, RLS и корректность тестовых режимов.

### Гистология, лекции и атлас
- Атлас использует существующий `content`; сохранить его внешний вид и подписи/описания препаратов.
- Требуемый просмотрщик: центрирование по области просмотра, масштабирование и перемещение изображения в любой точке, полноэкранный режим, кнопки лупы/масштаба, удобство на iPhone и ПК; изображения, схемы и таблицы должны оставаться читаемыми.
- Медиа оптимизировать без потери читаемости; видео — с Full HD качеством/вариантами, если исходник позволяет.
- Исторический импорт trainer cards: `data/content_packages/histology-mbh-trainer-cards.json` (206 карточек: 178 препаратов + 28 электронограмм); проверить миграции, пути изображений и корректные подписи.
- Исторически ожидались около 350 гистологических экзаменационных вопросов и дополнительно около 163 вопросов по цитологии/эмбриологии; не заменять существующие 20+20 вопросов. Повторно проверить актуальные количества в БД, публикацию, дубликаты и семестровую привязку.
- Лекция 5 «Кровь и лимфа»: возрастные нормы, физиологические перекрёсты, таблицы, мини-тесты по блокам, ссылки на тренажёр. Проверить тестовый маршрут `/tests/preparation/29564479-ebb7-4c81-9d0d-4e5ca640d053`.

### Файлы и хранение
- Не загружать большой архив целиком в ограниченную бесплатную Supabase DB/storage, если подходящее внешнее файловое хранилище уже настроено.
- Проверить B2 приватный бакет `medbiohim-files`, ключи, URL подписи, права доступа, лимиты, варианты/производные медиа и резервные пути.
- Проверить SpaceWeb структуру: медиа должны лежать в правильном месте относительно `config/`, `src/`, `public/`; PHP версия на сервере должна совпадать с требованиями.
- Исторические ошибки: отсутствующие B2-колонки, 404/502 trainer images, неверный путь `HISTOLOGY_MEDIA_ROOT`, несовместимость схемы/старых вопросов. Проверить текущую ситуацию, не считать все ошибки открытыми без повторной проверки.

### Сообщество, жалобы, админка и учебный план
- Жалоба должна быть доступна на каждом релевантном вопросе/тесте/материале и попадать в админ-панель.
- Админ-панель нужно развивать по категориям и реальным задачам модерации, не смешивая её с основным студенческим интерфейсом.
- Учебный план/предметы/семестр и прогресс должны быть связаны с текущим учебным контекстом и реальными данными.
- Исторически отмечались дублирующийся метод ContentStore, старые схемы вопросов и отсутствие отдельных RLS-политик; повторно проверить.

### Будущие интеграции
- Telegram: единый поток заданий, Mini App, безопасный вход/привязка, group mapping, идемпотентность, вложения, обработка фото/OCR с ручной проверкой.
- Browser extension для EIOS: сейчас это направление планирования/MVP быстрых ссылок, не считать готовым безопасным импортом. Будущий импорт должен быть явным действием пользователя, с предпросмотром, происхождением, дедупликацией и версиями.
- FESMU/официальные расписания: импортировать только после проверки доступности источника/правил и с понятным fallback, не полагаться на несуществующий API.
- NeoFamily lab: использовать как источник идей функциональности, а не как отдельную платформу/обязательную интеграцию.
- Все идеи сначала фиксировать в карте интеграций, затем в roadmap, затем реализовывать небольшими проверяемыми проходами.

## 8. Правило завершения работ

Функция считается завершённой только когда:
1. Код внедрён в правильную ветку без лишних веток.
2. Пройдены реальные тесты и проверки сборки.
3. Проверены отрицательные сценарии/права доступа.
4. Подтверждён путь UI → API → authorization → database → отображение результата.
5. При необходимости проверены мобильный и desktop сценарии.
6. Обновлены roadmap, phase status, sync stamp и unfinished registry.
7. Развёртывание/БД не изменяются без соответствующего разрешения, а секреты не попадают в чат/логи.

## 9. Точка продолжения после паузы

Начинать не с новых функций, а с проверки согласованности документов и блокирующих тестов:
1. Устранить противоречия в документации: некоторые старые абзацы в `docs/STUDENT-FIRST-MAP.md` и контракте описывают уже исправленные в исходниках ограничения как ещё открытые.
2. Восстановить runner GitHub Actions и получить реальное выполнение.
3. Проверить текущий diff и тесты Node/PHP, исправить найденные ошибки.
4. Проверить PHP маршрут ingestion и реальную конфигурацию окружения без публикации секретов.
5. End-to-end тест group homework с участником и посторонним.
6. Только после этого переходить к безопасной регистрации/привязке Telegram.
7. После каждой пачки — записать результаты, точные SHA коммитов, проверки и оставшиеся задачи в этот файл и в общую дорожную карту.

**Статус на момент паузы:** исходные изменения в `main` есть; тесты и production-поведение не подтверждены; автоматическая проверка блокируется на уровне запуска runner; Telegram Web App пока открывает сайт, а relay только передаёт групповые обновления. Никаких заявлений о полностью готовой Telegram-интеграции или зелёной CI-сборке делать нельзя.
