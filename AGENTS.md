# Инструкции для ИИ-агентов MEDBIOHIM

Этот файл — входная точка для любого агента, работающего с репозиторием. Перед изменениями прочитай его целиком.

## Источник истины и старт проверки

1. Работай от актуального `main`, а не от старого чата, аудита, PR или локального снимка.
2. В начале зафиксируй `git rev-parse HEAD`, `git status --short`, `git log -1 --oneline`; проверь чистоту рабочей копии и точный base commit.
3. Сверь затрагиваемые пути с текущим деревом `main`. Датированные документы (`docs/CURRENT-STATE-*`, аудиты, roadmap) — снимки на дату, а не гарантия текущего состояния.
4. Наличие кода не доказывает, что он задеплоен или принят на production.

## Контекст проекта

MEDBIOHIM — личный некоммерческий студенческий проект «от студентов для студентов», а не официальный сайт университета. Приоритет — самостоятельная подготовка студентов; ДЗ могут добавляться студентами вручную и через разрешённые интеграции.

Каноническая цепочка: Browser/PWA → Next.js на Vercel → same-origin `/api/v1/*` → Next.js proxy `src/app/api/v1/[...path]/route.ts` → Cloudflare Worker `medbiohim-api` (Hono) → Supabase / Upstash / файловый storage. `medbiohim-api-shadow` — compatibility fallback только для HTTP 501; `medbiohim-telegram` — отдельный Worker бота. PHP/SpaceWeb и `integrations/cloudflare-api/` — legacy, не считать production API.

## Параллельная работа

- Верхнеуровневые агенты работают в отдельных рабочих копиях/worktree; общий каталог с одновременной записью запрещён.
- Агенты независимы: не связываются друг с другом, не ждут чужих ответов и не читают чужие диалоги. Каждый получает самодостаточную задачу от координатора.
- Не создавай постоянные удалённые ветки по умолчанию. Результат параллельной работы — patch/diff и отчёт.
- После завершения независимых частей координатор назначает ровно одного интегратора. Он последовательно применяет патчи в отдельной integration workspace.
- `main` — единственная каноническая ветка. Не пушь в `main`, не создавай PR/ветки и не запускай production deploy без явного поручения. Commit в `main` выполняет только назначенный интегратор/maintainer после проверки и разрешения.
- Не удаляй существующие ветки и не сливай старые PR только потому, что они существуют.

## Безопасность и границы изменений

- Не читай, не выводи и не коммить реальные `.env`, токены, service-role keys, пароли, приватные URL с секретами или персональные данные. Используй `.env.example` и синтетические fixtures.
- Не выполняй production SQL, миграции, массовые импорты/удаления, загрузки в storage, изменение secrets, DNS, Worker/Vercel deployment или destructive-команды без отдельного явного разрешения.
- Supabase — canonical source of truth; Redis — cache/ephemeral state. SQL-файл не доказывает, что миграция применена.
- RLS и серверная авторизация обязательны. Скрытие кнопки во frontend не является проверкой доступа.
- Не меняй прикладной код, БД или инфраструктуру в задаче, ограниченной документацией.

## Проверки и отчёт

Используй реальные scripts из `package.json` и `workers/api/package.json`; не выдумывай команды. Для frontend доступны `npm run typecheck`, `npm run lint`, `npm test`, `npm run build`. Для Worker — `cd workers/api && npm run check`. Запускай релевантные проверки с установленными зависимостями и безопасным окружением.

В отчёте укажи base commit, изменённые пути, точные команды и результаты, что не проверено, риски и patch. Не называй работу завершённой, если изменения не интегрированы и не проверены.
