# MEDBIOHIM — отказоустойчивый хостинг и бесплатные тарифы
**Статус:** архитектурное предложение; ничего не переносить и не выключать до тестового пилота.  
**Обновлено:** 2026-10-11.

## 1. Цель
Сохранить текущую систему и дополнить её независимыми путями доступа:
1. Основной иностранный хостинг — текущий Vercel для сайта.
2. Второй независимый иностранный origin/hosting path — на случай, когда сайт не открывается у отдельного провайдера/оператора, но интернет в целом работает.
3. Отдельный хостинг webhook-бота, выбранный по пригодности для бесплатного постоянного приёма запросов, а не по максимальному количеству CPU/RAM.
4. Вторичный российский хостинг/статическая копия на случай блокировки/недоступности основных иностранных провайдеров. Обновление российского зеркала может быть отложенным, но должно иметь явный timestamp и предупреждение о возможной устарелости.

Текущие Vercel + Supabase + SpaceWeb + Backblaze B2 остаются основной системой. Не заменять их списком новых провайдеров и не переносить всю систему одним изменением.

## 2. Рекомендуемая целевая схема
```
Пользователь
  ├─ Primary: https://medbiohim.vercel.app (текущий Next.js/Vercel)
  ├─ Secondary foreign origin: независимый hosting/provider + отдельный URL
  └─ Emergency RU mirror: российский статический/совместимый хостинг + отметка свежести

Telegram
  └─ один Telegram webhook URL
       └─ Node/Worker relay
            └─ PHP API на SpaceWeb (основной источник операций)
                 └─ Supabase (основная база/auth)
                      └─ B2 / существующее хранилище медиа
```

Критически важно:
- Telegram Bot API доставляет обновления одному активному webhook URL на бота. Не регистрировать один bot token одновременно на двух независимых webhook. Для резервирования менять webhook контролируемо либо использовать один стабильный gateway с собственным failover.
- Secondary site — не полноценный failover, если он всё ещё зависит от Vercel, того же домена/DNS, Supabase или PHP API, который недоступен. Нужно описать отдельно, что работает при отказе каждого слоя.
- Не хранить две независимо редактируемые базы. Supabase остаётся источником истины; read-only зеркало может содержать публичные учебные материалы, но не личные данные, оценки, токены или приватные задания.
- Никакого автоматического переключения записи на две базы без репликации, конфликт-резолвинга и тестов.
- Бесплатные тарифы меняются и могут требовать подтверждения телефона, лимитов/квот или карты в отдельных сценариях. Перед выбором перепроверять актуальные условия; не обещать абсолютную бесплатность/uptime.

## 3. Предварительный выбор по ролям

### A. Webhook Telegram: Cloudflare Workers — первый кандидат на PoC
Почему:
- Serverless webhook подходит для событийной нагрузки и не требует постоянно работающего VPS.
- Может работать отдельно от Vercel, что уменьшает риск единого хостингового отказа.
- Не нужно держать тяжёлую Node-процесс-службу постоянно включённой.

Ограничения и обязательная проверка:
- Проверить текущие бесплатные лимиты, ограничения CPU/размера, совместимость кода и Node APIs, секреты и логирование перед внедрением.
- Worker не должен заменять PHP API или Supabase; сначала это только Telegram webhook/relay.
- Верифицировать Telegram secret header и PHP shared secret; ограничить размер тела и время ожидания; не логировать сообщения с персональными данными.
- Реализовать идемпотентность по Telegram `update_id`, безопасные повторы и ограничение частоты.
- Протестировать вызовы PHP API из выбранного региона и доступность из сетей, которыми пользуется группа.
- Если Cloudflare сам недоступен у конкретного провайдера, бот может перестать получать webhook; отдельный URL сам по себе не гарантирует доступность.

**Решение:** лучший первый кандидат для бесплатного webhook PoC, не финально утверждённый production выбор до теста.

### B. Сайт: оставить Vercel основным, проверить Cloudflare Pages как независимый вторичный origin
- Vercel уже связан с GitHub и подходит для текущего Next.js сайта; не ломать автодеплой.
- Cloudflare Pages хорош для статического фронтенда, но не считать автоматически полной заменой Vercel для всего Next.js SSR/API. Проверить фактические server components, route handlers, middleware, image optimization, auth callbacks и env vars.
- Если приложение требует серверного Next.js, оценить поддерживаемый Cloudflare adapter/OpenNext или другой независимый hosting с актуальной совместимостью. Не переводить приложение на чистую статику, если от этого ломается авторизация или динамические страницы.
- Secondary origin должен иметь собственный URL и deploy pipeline из того же main commit; показать commit/build timestamp. Секреты и env vars настраиваются отдельно.
- Не использовать DNS-only failover как единственный план: пользователь может не открыть сам DNS/домен или основной провайдер может быть недоступен. Сохранить отдельный backup URL, который можно открыть вручную.
- Проверить CORS, callback/redirect URLs, cookie scope, CSP, Supabase allowed URLs, upload endpoints и canonical URL. Два домена могут ломать auth, cookies и внешние интеграции.

**Решение:** Vercel primary, Cloudflare Pages/совместимый hosting — PoC secondary после build compatibility audit.

### C. Российский emergency fallback
Кандидаты из пользовательского списка для отдельной проверки:
- ONREZA — заявлен как hosting для Next.js/SSR; подтвердить совместимость и актуальные условия.
- Layero — проверить поддерживаемый runtime и бесплатный лимит.
- GitVerse Pages / SourceCraft Sites / GitHub Pages — только для статического emergency snapshot; не считать полным динамическим приложением.
- Beget/другой российский hosting — оценить бесплатный тариф, ограничения PHP, лимит файлов/CPU и необходимость телефона/карты.
- S3-совместимый российский объектный storage — только для статики и публичных материалов, если условия бесплатности/стоимости подтверждены.

Российский fallback:
- Вторичный, не источник истины.
- Сначала допустим read-only snapshot публичных учебных материалов/инструкций, без Supabase credentials, приватных файлов, личных данных и записи прогресса.
- Показывать дату/commit последнего обновления и сообщение «резервная копия; данные могут быть устаревшими».
- Позже можно протестировать полноценный frontend deploy, но только если Next.js/Auth/API архитектура реально поддерживается.
- Обновления из GitHub main автоматически после успешных checks; если CI сломан — не выпускать автоматически потенциально неисправный snapshot.

### D. Остальные сервисы из предложенного списка
Не подключать сразу:
- FPS.ms: необходимость продлевать бесплатную машину каждые 24 часа делает его ненадёжным для постоянного бота.
- Hugging Face Spaces: полезен для публичного demo/AI prototype, не очевидный выбор для приватных учебных данных и постоянного webhook.
- Render: сон/пробуждение может добавить задержку; проверить текущую политику бесплатного тарифа.
- Railway: кредитная модель может перестать быть бесплатной; не считать постоянным бесплатным hosting.
- Replit Starter: лимиты проектов/публикаций и условия могут меняться; не первая опция для критического webhook.
- Deta Space: не считать доступным, пока не подтверждён статус продукта и условия.
- Netlify: можно рассмотреть для независимого статического frontend; проверить лимиты и Next.js runtime.
- GitHub Pages: только статические файлы; не PHP API/SSR/секреты.
- Telebot Creator / FreeTierBot / rawhq / Prisma Compute / Restate Cloud / jsdeck / AgentScale / Cloudflare Drop: оставить в backlog до проверки актуального существования, доступности, условий, приватности, сна, времени жизни deployment и подходящего runtime. Временные deploy на 1 час или обязательное продление не годятся для production.
- Не запускать одновременно много альтернативных сервисов: это повышает сложность, количество секретов и вероятность рассинхронизации.

Указанные пользователем цифры/лимиты — входные предположения, а не подтверждённые действующие условия. Перед PoC их надо перепроверить по официальной документации провайдера.

## 4. Ускорение загрузки: что проверять прежде нового хостинга
Проблема описана как долгий путь загрузки между Vercel и SpaceWeb. Не переносить сервис вслепую; сначала определить bottleneck:
1. Собрать Web Vitals и Network waterfall на мобильной сети и Wi-Fi: DNS/TLS, TTFB, JS hydration, API, media.
2. Разделить latency сайта, PHP API и загрузки медиа. Записать время отдельно для Vercel, SpaceWeb, Supabase и B2.
3. Изображения/атлас: проверять размер файла, responsive srcset, lazy loading вне первого экрана, кеширование и CDN; не ухудшать читаемость подписей и таблиц.
4. API: проверить последовательные вызовы, лишние round trips, N+1 запросы, таймауты, холодный старт/connection setup и размеры ответов.
5. Добавить server-side request IDs и измерения длительности без записи секретов/персональных данных.
6. Кешировать только подходящие публичные/редко меняющиеся данные. Не кешировать персональные данные и результаты тестов публично.
7. После измерений оптимизировать существующую цепочку; новый хостинг — не замена профилированию.

## 5. Бесплатная стратегия
- Не добавлять платный AI в обязательный путь.
- Базовые тесты, расписание, homework и Telegram commands должны работать без платного AI API.
- Использовать бесплатные квоты Vercel/Supabase/Cloudflare только в рамках текущих условий.
- Не создавать дополнительные оплачиваемые сервисы, домены, базы или платные egress-пути без согласования.
- Мониторить квоты, build minutes, storage, egress, invocations, logs; настроить graceful degradation, чтобы превышение квоты необязательного сервиса не ломало основной сайт.
- «Бесплатно без карты» перепроверяется отдельно на момент регистрации: география, верификация телефона, custom domain и антифрод-проверки могут менять требования.

## 6. Порядок внедрения
1. Baseline: измерить скорость текущей системы и составить dependency map.
2. Проверить GitHub Actions и добиться зелёного build/test на main.
3. PoC Cloudflare Worker: только webhook/relay, тесты подписи, update_id dedupe, retry, secret rotation; без production переключения.
4. PoC вторичного иностранного сайта: деплой из того же main commit, read-only сначала, тестировать Next.js/Auth/API compatibility и разные сети.
5. PoC российского статического emergency snapshot: только публичные материалы, явный timestamp, без секретов/личных данных.
6. Документировать процедуру ручного переключения и возврата на primary; провести учебный failover test.
7. Только после подтверждения результата принять решение о production.
8. Обновлять `ROADMAP.md`, `PHASES_STATUS.md`, `SYNC_STAMP.md` и `docs/UNFINISHED-REGISTRY.md`.

## 7. Acceptance criteria
- Измерена скорость до/после на мобильной сети и Wi-Fi.
- Сайт открывается по primary и secondary URL из независимых сетей.
- Secondary не требует доступа к primary hosting для отдачи своего frontend bundle.
- Все динамические функции, которые заявлены как поддерживаемые, проходят реальные тесты; иначе secondary маркируется как read-only snapshot.
- Supabase remains single source of truth; нет двойной записи и утечки секретов.
- Telegram webhook имеет одну зарегистрированную точку входа и проверенную схему relay/failover.
- Показан timestamp/commit вторичной копии.
- Условия тарифа и фактические лимиты подтверждены официальной документацией на дату PoC.
- Сценарий отказа проверен и rollback описан.
