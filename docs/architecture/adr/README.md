# Архитектурные решения (ADR)

Здесь фиксируются решения, которые дорого переигрывать: границы модулей,
контракты, кэш, права, форматы данных. Не «что сделали», а **почему так** и
**чем это держится**.

## Когда нужен ADR

- меняются границы модулей или публичная поверхность (`index.ts` баррель);
- вводится/меняется контракт API или схема данных;
- добавляется инфраструктурное поведение (кэш, очереди, ретраи, права);
- принимается решение «оставить как есть», хотя аудит предлагал переделать.

Не нужен: перенос файла без изменения поведения, правка копирайта, багфикс в
пределах одного модуля.

## Правила

1. Номер — следующий свободный, четыре цифры. Имя файла: `NNNN-kratkoe-imya.md`.
2. Запись после принятия **не переписывается**: изменение оформляется новым ADR,
   старый получает статус «заменено ADR-NNNN».
3. В записи обязателен раздел «Проверка» с реальными командами и честным
   перечислением того, что не проверялось.
4. Если решение проверяется машиной — ссылка на тест или скрипт обязательна.
   Решение без проверки считается пожеланием, а не архитектурой.
