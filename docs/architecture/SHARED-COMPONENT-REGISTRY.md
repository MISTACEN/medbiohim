# Реестр общих компонентов MEDBIOHIM — контракт

> **Статус:** контракт зафиксирован 2026-11-05 (этап A целевой архитектуры), состав дополнен этапами B–D. База — `main` = `8524a1f1`.
> Компоненты не переносились, прикладной код, БД, RLS и API не менялись: это фиксация схемы и начального состава.
> Данные реестра — [registry/components.json](registry/components.json). Проверка — `node --test test/component-registry.test.mjs` (входит в `npm test`).

## 1. Назначение

Реестр отвечает на вопросы: какие общие элементы существуют, в каком состоянии они находятся, кто их владелец, какие модули вправе их подключать, какая версия считается публичной и что изменилось между версиями.

Реестр — это **данные и контракт**, а не каталог файлов и не замена документации. Код компонентов остаётся там, где он лежит сейчас (`code_paths` только ссылается на путь).

## 2. Границы: чего реестр не делает

- **Не управляет доступом.** Права остаются в `user_roles`, RLS и серверных проверках. Поле `permissions` описывает, каким ролям разрешено использовать элемент в контенте, но само по себе ничего не разрешает.
- **Не версионирует контент.** Версии созданного контента — в `content_versions` и `workshop_item_versions`.
- **Не является хранилищем файлов, медиа или вопросов.**
- **Не заменяет API-контракты** (`API-CONTRACTS.md`) и не описывает маршруты.
- **Не требует переноса файлов.** Запись в реестре не означает, что компонент уже лежит в `src/shared/`.

## 3. Запись реестра

| Поле | Тип | Обязательное | Правила |
|---|---|---|---|
| `id` | string | да | `^[a-z][a-z0-9-]*(\.[a-z0-9-]+)+$`, уникальный, стабильный: не меняется при переносе кода |
| `title` | string | да | Человеческое название |
| `description` | string | да | 1–2 предложения: что делает и для чего |
| `type` | enum | да | См. §4 |
| `version` | semver | да | `MAJOR.MINOR.PATCH`, см. §5 |
| `status` | enum | да | `active`, `experimental`, `deprecated`, см. §8 |
| `code_paths` | string[] | да | Пути от корня репозитория; должны существовать |
| `params` | object[] | нет | `{name, type, required, description}` — публичные параметры, не внутренности |
| `compatible_modules` | string[] | да | Модули из §4 или `"*"` |
| `permissions.edit` | string[] | да | Инженерные роли: `frontend`, `backend`, `database`, `education`, `storage`, `devops`, `qa` |
| `permissions.use` | string[] | да | `admin`, `teacher`, `student` или `"*"` |
| `owner` | string | да | Кто пишет компонент и отвечает за контракт |
| `since` | `YYYY-MM-DD` | да | Дата регистрации |
| `notes` | string | нет | Ограничения, долги, известные дубли |
| `replaced_by` | string \| null | для `deprecated` | `id` заменяющего элемента |

Инварианты:

- два активных элемента не могут делить один и тот же файл;
- `id` не переиспользуется после удаления;
- `code_paths` для `active` и `experimental` обязаны существовать — иначе контракт ссылается на мёртвый код.

## 4. Перечисления

**Типы:** `ui-primitive` (кнопки, окна, поля, таблицы, состояния), `media` (изображения, видео, читалки), `content-block` (учебный блок), `question-type` (тип вопроса: модель, рендер, проверка), `editor` (редактор контента), `schema` (общая структура данных), `template` (шаблон страницы/контента), `utility` (хук или чистая функция).

**Статусы:** `active`, `experimental`, `deprecated`.

**Модули:** `subjects`, `tests`, `lectures`, `materials`, `trainers`, `assignments`, `schedule`, `progress`, `teaching`, `admin`, `atlas`, `labs`. `"*"` допускается только для элементов, не зависящих от предмета и роли (базовые примитивы, хуки).

## 5. Версионирование

- **MAJOR** — ломающее изменение публичного контракта: обязательный параметр, удалённый параметр, изменение формата данных, изменение поведения проверки, удаление экспорта.
- **MINOR** — добавление возможности без изменения существующего поведения (новый необязательный параметр, новый вариант отображения).
- **PATCH** — исправление без изменения контракта.

Правила регистрации существующего кода: `1.0.0`, если контракт уже используется за пределами модуля-владельца; `0.x`, если потребителей почти нет или поведение ещё меняется. Версия реестра (`schema_version`) версионируется отдельно от версий компонентов.

Обновление компонента не должно менять уже созданный контент: если новая версия меняет вид или разметку, старое поведение сохраняется или контент мигрируется отдельным решением.

## 6. Совместимость

Список модулей — явный allowlist. Чтобы подключить элемент в новом модуле, запись обновляется (MINOR). Убирать модуль из списка можно только вместе с проверкой, что он больше не использует элемент (MAJOR).

Совместимость не выводится из расположения файла: элемент может лежать в `src/components/admin/`, но быть совместимым только с `admin` — пока не доказано обратное.

## 7. Права

Две независимые плоскости:

- `permissions.edit` — кто меняет реализацию (инженерное владение, согласуется с `AGENT-OWNERSHIP.md`);
- `permissions.use` — какие роли могут использовать элемент в своём контенте (например, `admin` и `teacher` для редактора лекции).

Контроль доступа обеспечивают сервер и RLS. Реестр не является вторым источником прав: если роль не входит в `use`, сервер всё равно обязан отклонить операцию, а если входит — не освобождает от проверки владения контентом.

## 8. Статусы

- `experimental` — контракт может меняться, потребителям нельзя опираться на детали; в интерфейсе допустимо показывать как «бета».
- `active` — контракт стабилен, изменения только по §5.
- `deprecated` — элемент не рекомендуется, но не удаляется, пока есть потребители; обязательны `replaced_by` или причина в `notes`.

Понижение статуса (`active` → `experimental`) допускается с записью причины в `notes`. Удаление записи — отдельное решение, не следствие изменения кода.

## 9. Хранение и эволюция

Сейчас единственный источник — `docs/architecture/registry/components.json` (плюс этот документ). Это осознанно временно: на этапе A файлы не переносятся и БД не меняется.

Порядок перехода, если реестр понадобится во время выполнения:

1. аддитивная миграция таблицы реестра (идентификаторы и версии сохраняются);
2. чтение через каноническую цепочку `/api/v1/*` → Worker → Supabase, а не прямое подключение из браузера;
3. JSON остаётся синхронизированным источником для теста либо превращается в fixture;
4. второй реестр в коде не создаётся: существующие локальные списки (например, `BlockKind`/`BLOCK_LABELS` в редакторе лекций) поглощаются реестром на этапе E, а не живут параллельно.

## 10. Процедура изменения

1. Проверить, нет ли уже записи с тем же компонентом (по коду и по смыслу).
2. Определить `id` и тип; для существующего кода — заполнить `code_paths`.
3. Назначить версию по §5 и статус по §8.
4. Заполнить `compatible_modules` (явно, без `"*"` по умолчанию).
5. Заполнить `permissions.edit` и `permissions.use`.
6. Обновить `registry/components.json` и, если изменился контракт, этот документ.
7. Прогнать `node --test test/component-registry.test.mjs`.

Этап B (`question-type.registry`) закрывает модель и проверку, этап C — панель результата и единый вариант ответа с тремя формами (`button`, `choice`, `row`): на общий код переведены прохождение теста, практика, билеты, банк, карточка тренажёра, мини-тест лекции и тест физиологии. Списки с собственной семантикой (`SubjectQuestionBank`), лента тренажёров, редакторы, порталы и лаборатории сохраняют свою раскладку и будут унифицированы отдельным проходом.

Этап D (`ui.button`, `ui.modal`, `ui.badge`, `ui.tabs`) добавляет баррель `src/components/ui/index.ts` и переносит `DataTable` в общий слой. Примитивы собирают существующие классы `.btn-*` / `.badge-*`, поэтому их подключение не меняет вид; на общий слой уже переведены `useConfirm` (все нативные `window.confirm` заменены, включая мастерскую, настройки, лабораторные и подготовку к тесту), `Tabs` в закладках и химической лаборатории, `Modal`/`Button` в отчёте об ошибке и трёх админских формах, `Badge` в статусе публикации теста. Массовая замена остальных 133 кнопок, ручных модалок и плашек не выполнялась: это постепенный проход, а не часть контракта реестра.

## 14. Как проверяется

`node --test test/component-registry.test.mjs` (входит в `npm test`) проверяет:

- существование контракта и данных, `schema_version` и `updated_at`;
- уникальность и формат `id`;
- допустимые `type`, `status`, semver-версию;
- существование всех `code_paths`;
- отсутствие двух активных записей на одном файле;
- непустые и допустимые `compatible_modules`, `permissions.edit`, `permissions.use`;
- наличие `replaced_by` или причины у `deprecated`.

`node --test test/ui-barrel.test.mjs` проверяет, что баррель `src/components/ui/index.ts` экспортирует каждый файл каталога и не ссылается на удалённые.

Тест не проверяет вёрстку, поведение и доступность компонентов: примитивы этапа D покрыты отдельными тестами `src/components/ui/__tests__/primitives.test.tsx` (`npm run test:unit`), остальное — задача этапов B–E.
