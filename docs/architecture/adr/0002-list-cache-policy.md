# ADR-0002. Кэш списочных ответов: TTL + stale-while-revalidate

- **Статус:** принято
- **Дата:** 2026-11-19
- **Этап плана:** P2 (инфраструктура API)
- **Затрагивает:** `workers/api/src/lib/cache.ts`,
  `workers/api/src/lib/pagination.ts`, `workers/api/src/routes/subjects.ts`,
  `workers/api/test/cache.test.js`, `workers/api/test/pagination.test.js`

## Контекст

Каталог предметов (`GET /api/v1/subjects`) читается почти каждой страницей:
навигация, карточка предмета, админка. Запрос всегда идёт в Supabase и каждый
раз тянет до 500 строк, хотя меняется каталог редко. Upstash Redis в воркере уже
подключён и используется для rate limit (`lib/redis.ts`), но для чтения данных не
применялся.

Отдельная проблема — размер ответа: контракт `{ items }` без пагинации. Менять
его нельзя (клиенты и тесты рассчитывают на текущую форму), но у тяжёлых
потребителей должна быть возможность взять страницу.

## Решение

1. **Кэш** — `lib/cache.ts`: именованные политики `{ ttlSeconds, staleSeconds }`,
   конверт значения `{ at, value }`, ключ `cache:v1:<политика>:<hash>` c
   сортировкой параметров.
   - свежая запись → ответ из кэша;
   - устаревшая → ответ из кэша сразу, обновление в `c.executionCtx.waitUntil`;
   - промах → загрузчик, запись в кэш (TTL = `ttl + stale`).
   - **fail-open:** нет Redis или он отвечает ошибкой — запрос идёт в БД, как
     будто кэша нет. Кэш не может быть причиной 5xx.
2. **Пагинация** — `lib/pagination.ts`: `limit`/`offset` **необязательные**.
   Если клиент их не передал (`requested: false`), тело ответа байт-в-байт
   прежнее: `{ items }`. Если передал — `{ items, page: { limit, offset, total,
   has_more } }`. Мусор в параметрах не роняет запрос: значения зажимаются.
3. В `GET /subjects` кэшируется выборка строк из Supabase, а дедупликация по
   слагу выполняется уже после кэша — она дешёвая и зависит от бизнес-правила,
   которое может меняться без инвалидации кэша.

Применение (дополнено 2026-11-20): `subjects:catalog` (первоначально),
`chem:resolve` — `GET /chemistry/resolve`, публичный прокси PubChem,
одинаковый ответ на одинаковый query, null кэшируется как «не найдено»;
`external:stats` — `GET /external-platforms/stats`, публичный агрегат,
без кэша читал до 5000 строк на каждый запрос.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| `Cache-Control`/CDN-кэш на клиенте | не помогает воркеру и не работает для авторизованных ответов с разными ролями |
| Кэш без stale: только TTL | любой промах — ожидание Supabase; при 2-минутном TTL это заметно на каждом холодном окне |
| Обязательные `limit`/`offset` | ломает контракт и всех клиентов; несовместимо с правилом «API не меняем» |
| Кэшировать весь HTTP-ответ | в ответе `requestId`, он обязан быть уникальным на запрос |

## Последствия

**Положительные:** каталог перестаёт ходить в БД на каждый рендер; ответ не
зависит от доступности Redis; тяжёлые потребители могут листать список, не
получая 500 строк.

**Отрицательные и риски:**
- до `ttl + stale` секунд админ может видеть старый каталог. Для каталога
  предметов это приемлемо (правки редки и не критичны по времени), но
  **нельзя** применять эту политику к данным, где важна свежесть: сдачи,
  оценки, сообщения;
- ключ кэша не знает про роль пользователя — политику можно включать только для
  ответов, одинаковых для всех ролей (каталог активных предметов). Ветка
  `include_inactive` имеет отдельный ключ, но включать её в общий кэш нельзя без
  проверки прав;
- `waitUntil` доступен не во всех средах (тесты, скрипты) — без него обновление
  выполняется синхронно, ответ всё равно берётся из кэша.

## Проверка

```bash
cd workers/api
node --test test/cache.test.js test/pagination.test.js
npm run check
```

Тесты покрывают: стабильность ключа, свежесть, stale-while-revalidate с
`waitUntil`, обновление без `waitUntil`, ошибку загрузчика на обновлении,
fail-open без Redis, битое значение в кэше, границы `limit`/`offset` и
неизменность формы ответа без параметров.

**Не проверялось:** живой Upstash и прод-нагрузка (нет доступа к окружению),
поведение при гонке двух параллельных обновлений (допускается двойной вызов
загрузчика — данные одинаковые).

## Откат

Убрать вызов `cached(...)` в маршруте (вернуть прямой запрос) или передать
`store: null`. Ключи `cache:v1:*` истекают сами по TTL; ручная очистка не нужна.
