# MEDBIOHIM — скрытый функциональный аудит: Pass 1 + Pass 2 — 2026-10-06

## Цель

Этот аудит не проверяет только наличие кода. Проверяется более строгая цепочка:

**ожидаемая функция → точка входа в UI → контекст действия → API → БД → админ/модерация → обратная связь пользователю → завершение процесса.**

Особый фокус:
- жалобы и сообщения об ошибках;
- тесты, банк вопросов и подготовка;
- админ-панель;
- права и контекст пользователя;
- пустые/нулевые данные;
- скрытые разрывы между уже существующим backend и фактическим UX;
- устаревшие документы как источник неправильных решений.

# PASS 1 — инвентаризация ожидаемых функций

## 1. Жалоба на вопрос

### Что найдено

Функция уже существует:

- `QuestionReport` подключён к обычному тесту;
- подключён к preparation;
- подключён к полному банку;
- API: `POST /api/v1/questions/{id}/report`;
- категории: неверный ответ, формулировка, несколько правильных, нет правильного, опечатка, другое;
- есть защита от повторной одинаковой жалобы;
- админ-центр: `/admin/problems`;
- есть статусы new/reviewing/fixed/rejected;
- есть `content_work_items` для рабочих задач.

### Что нельзя считать закрытым

Жалоба сейчас передаёт в основном:

`question_id + category + message`.

Для реального исправления этого недостаточно.

Администратору потенциально нужно видеть:

- какой тест;
- какой банк;
- какой режим: prepare / solve / exam / sequential;
- номер вопроса в конкретной попытке;
- текст вопроса на момент жалобы;
- варианты ответа на момент жалобы;
- ответ студента;
- был ли ответ отмечен правильным/неправильным;
- session_id;
- test_id;
- время;
- пользователь/группа;
- источник вопроса.

Иначе студент сообщает «ответ неправильный», а администратор открывает уже изменённый вопрос и не видит, **что именно видел студент**.

### Статус

**🟡 Частично готово.**

### Требование

Сделать report context snapshot.

Минимум:

`report → question → test → preparation_session → user → submitted_answer`

Для жалобы из банка без попытки допускается:

`report → question → bank/test context`.

# 2. Обратная связь после жалобы

Сейчас пользователь получает сообщение:

«Сообщение отправлено. Спасибо!»

Но нет полноценного жизненного цикла:

`создано → принято → проверяется → исправлено/отклонено → пользователь уведомлён`.

### Gap

Нет подтверждённого механизма:

- уведомить студента, что проблема принята;
- показать историю его жалоб;
- сообщить «исправлено»;
- дать админу оставить внутренний комментарий;
- отличить комментарий студента от внутренней заметки.

### Статус

**🟡 Product gap.**

---

# 3. Тест → жалоба

Кнопка жалобы действительно присутствует непосредственно возле текущего вопроса.

Это хорошо.

Но acceptance должен проверять не только наличие кнопки:

1. открыть тест;
2. ответить;
3. нажать «Сообщить об ошибке»;
4. отправить;
5. обновить страницу;
6. открыть admin/problems;
7. найти жалобу;
8. увидеть исходный контекст;
9. создать работу;
10. исправить вопрос;
11. закрыть жалобу;
12. убедиться, что статус не расходится с work item.

Сейчас это **не доказано end-to-end**.

# 4. Админ-панель

## Найденная архитектурная проблема

Админка уже выросла до нескольких разных классов инструментов:

- overview;
- расписание;
- предметы;
- группы;
- пользователи/роли;
- объявления;
- тесты;
- вопросы;
- экзаменационные билеты;
- лекции;
- проблемы/жалобы;
- импорт Excel;
- импорт content package;
- database/Excel;
- материалы;
- trainer cards;
- Telegram;
- health;
- presence;
- validation;
- работы/задачи.

При этом часть находится в `/admin`, часть в `/admin/tools`, часть в отдельных редакторах.

### Проблема

Это уже не «одна админка», а набор инструментов без единой информационной архитектуры.

Особенно плохо:

- «ДЗ / медиа» смешивает разные задачи;
- «Импорт / tools» слишком широкое название;
- database editor фактически является low-level административным инструментом;
- problems/work items не являются частью единой очереди задач;
- Telegram находится отдельно от группы/пользователей/ДЗ;
- content validation находится в tools, хотя относится к контролю качества контента;
- quick-edit вопросов распределён между несколькими экранами.

### Требуемая новая структура

**1. Главная**
- состояние системы;
- критические ошибки;
- новые жалобы;
- незавершённые работы;
- контентные проблемы;
- последние изменения.

**2. Учебная структура**
- группы;
- пользователи;
- предметы;
- учебный план;
- расписание;
- посещаемость.

**3. Контент**
- тесты;
- вопросы;
- экзаменационные вопросы;
- билеты;
- материалы;
- тренажёры;
- лекции.

**4. Модерация**
- жалобы;
- работы;
- пользовательский контент;
- спорные/неподтверждённые материалы.

**5. Интеграции**
- Telegram;
- AI;
- файлы/SpaceWeb;
- внешние сервисы.

**6. Импорт / миграция**
- Excel;
- content package;
- массовые операции;
- dry-run;
- validation.

**7. Система**
- health;
- presence;
- audit log;
- DB tools;
- rollback;
- диагностика.

Low-level Database/Excel нельзя оставлять рядом с обычными учебными кнопками без предупреждения и защиты от массовой ошибки.

# 5. Админка: скрытая проблема прав

Наличие `hasToken()` в frontend не означает административную авторизацию.

Правильная граница должна быть:

**UI скрывает → backend дополнительно проверяет роль → DB RLS ограничивает данные.**

Backend для problem center использует RequireAuth + RequireRole(admin), что правильно.

Но для всей админки нужен единый audit:

- каждый admin endpoint;
- роль;
- допустимые действия;
- RLS;
- destructive operation;
- audit log.

# 6. Рабочие задачи по жалобам

Сейчас:

`жалоба → создать work item → изменить status`.

### Скрытые gaps

- нет полноценного assignee UX;
- нет SLA/priority queue;
- нет внутреннего комментария;
- нет истории изменений work item в UI;
- нет гарантированного согласования report.status и work.status;
- «Исправлено» может закрыть жалобу до фактического завершения работы;
- нет доказательства пользователю, что исправление действительно попало в опубликованный контент.

### Нужная модель

`Report`
→ `Review`
→ `Work item`
→ `Edit`
→ `Validation`
→ `Publish`
→ `Report resolved`
→ `student notification`.

# 7. Тесты и подготовка

Проверено:

- full;
- count;
- sequential;
- сохранение ответа;
- восстановление позиции;
- завершение;
- AI review;
- номера вопросов;
- multiple correct;
- open answers;
- жалоба.

### Но есть скрытый риск

В preparation ответ сохраняется отдельно от report.

Поэтому жалоба не знает, какой ответ был выбран.

Для пользователя это выглядит цельно:

**«я ответил → увидел ошибку → пожаловался»**

но backend сейчас хранит эти действия как независимые сущности.

Это нужно связать через context.

---

# 8. Пустая БД не означает рабочую функцию

Живой Supabase сейчас:

- `question_reports = 0`;
- `content_work_items = 0`;
- `test_preparation_sessions = 7`;
- `test_preparation_results = 0`.

Ноль жалоб и работ не является дефектом сам по себе.

Но он означает:

**цепочка report → admin → work → resolve ещё не доказана реальными данными.**

Следовательно, такие функции нельзя помечать DONE только потому, что backend и UI существуют.

# 10. Очень важный обнаруженный drift документации

Документация проекта содержит несовместимые контрольные цифры.

Например:

- ROADMAP / PHASES / SYNC_STAMP всё ещё содержат старые значения вроде **350 exam_questions** и **27 materials**;
- более поздние audit/content-matrix записи содержат другие значения;
- последний live audit также даёт другие цифры.

Это не косметическая проблема.

Это означает, что разные документы могут давать разработчику разные «источники истины».

### Новое правило

Нельзя вручную писать текущие counts в ROADMAP.

Нужен один:

**LIVE PROJECT SNAPSHOT**

с датой проверки и SQL/query source.

ROADMAP должен содержать только статус и ссылку на snapshot.

# 11. Другие скрытые классы проблем, которые теперь считаются отдельным аудитом

Для каждой функции проверять:

### UI completeness
- есть ли кнопка;
- есть ли empty state;
- есть ли loading;
- есть ли error;
- есть ли retry;
- есть ли disabled state;
- есть ли mobile state.

### Context completeness
- кто;
- группа;
- предмет;
- занятие;
- источник;
- конкретная попытка;
- конкретный объект.

### Persistence
- создаётся ли запись;
- можно ли восстановить состояние;
- нет ли duplicate;
- нет ли race condition.

### Authorization
- UI;
- API;
- RLS.

### Lifecycle
- create;
- review;
- edit;
- publish;
- archive;
- delete;
- restore;
- history.

### Feedback
- пользователь знает, что действие выполнено;
- админ получает действие;
- пользователь может узнать результат.

### Recovery
- refresh;
- expired token;
- network error;
- backend 500/503;
- повторная отправка.

**«если endpoint и кнопка есть — функция готова».**
