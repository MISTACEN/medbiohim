# ADR-0001. Реестр подмодулей предметов как источник истины

- **Статус:** принято
- **Дата:** 2026-11-19
- **Этап плана:** A2 / P2 (модульная архитектура, §4)
- **Затрагивает:** `src/modules/subjects/`, `src/app/subjects/[id]/page.tsx`,
  `scripts/new-module.mjs`, `test/subject-submodules.test.mjs`

## Контекст

Химия — предмет, а не раздел платформы, но её разделы (структуры, реакции,
растворы, лаборатория, практика, таблица элементов) были объявлены в трёх
независимых местах:

1. `ChemistryModule.tsx` — массив `SECTIONS` для панели внутри лекции;
2. `src/app/subjects/[id]/page.tsx` — навигация карточки предмета, где химия
   определялась регуляркой `/chem|хим/i` по слагу и названию;
3. `src/app/chemistry/*` — отдельные страницы разделов.

Добавление второго предмета с разделами требовало правки всех трёх мест, а
расхождение между ними не ловилось ни одним тестом: регулярка могла включить
«Структуры» предмету, у которого нет ни одного компонента химии, и это
обнаруживалось только в браузере.

## Решение

Данные о подмодулях живут в одном файле — `src/modules/subjects/registry.json`
(слаг, заголовок, описание, слаги предметов из БД, вкладки с подписью,
подсказкой и ссылкой на страницу). Читают его через типизированный доступ
`src/modules/subjects/registry.ts`, наружу модуль отдаёт только баррель
`src/modules/subjects/index.ts`.

- Реестр — чистые данные, без JSX и без сетевых вызовов: его можно
  импортировать и в серверный, и в клиентский компонент.
- Карточка предмета определяет подмодуль через `submoduleForSubject(slug)`;
  прежняя регулярка осталась только как запасной вариант для предметов, которых
  в реестре нет.
- Новый подмодуль создаётся генератором `scripts/new-module.mjs`: он пишет
  каталог, баррель, скелет UI и запись в реестр, отказываясь перезаписывать
  существующее.
- Скелет UI читает вкладки из реестра, поэтому добавление раздела — правка
  JSON, а не кода.

## Альтернативы

| Вариант | Почему не выбран |
|---|---|
| Оставить разделы в `ChemistryModule` и расширять его пропсами | каждый новый предмет тянул бы химический компонент; границы модуля размываются |
| Реестр как TS-массив в `registry.ts` | генератору пришлось бы править код (хрупкие текстовые вставки); JSON правится и проверяется данными |
| Динамическая регистрация во время выполнения (`registerSubmodule` при импорте) | порядок импортов влияет на состав навигации, SSR и клиент расходятся |
| Оставить регулярку по названию | именно она и давала ложные «Структуры» предметам без химии |

## Последствия

**Положительные:** один источник истины для разделов; новый предмет — запись в
реестре; навигация карточки перестала зависеть от названия предмета; данные
проверяются тестом, а не глазами.

**Отрицательные и риски:** `ChemistryModule` всё ещё содержит свои подписи и
подсказки — они дублируют реестр. Пока дублирование есть, тест сверяет порядок
ключей и дословный текст подписей с UI, поэтому расхождение падает в CI. Полный
перенос текстов в реестр — отдельный шаг: он меняет UI-код, а этот ADR
фиксирует только источник истины.

## Проверка

```bash
node --test test/subject-submodules.test.mjs
node --test test/module-boundaries.test.mjs
npm run typecheck
```

Тест проверяет: уникальность слагов и вкладок, отсутствие предмета у двух
подмодулей, существование страниц по `href`, совпадение вкладок химии с
`SECTIONS` по порядку и дословно, отказ генератора на занятом слаге.

**Не проверялось:** открытие карточки предмета в браузере (нет живого
окружения в этом заходе), поведение на данных прода (в БД не ходили).

## Откат

Удалить `src/modules/subjects/registry.json` и `registry.ts`, вернуть
`submoduleForSubject` в карточке предмета на регулярку. Записи реестра — данные
в репозитории, миграций нет.
